# 最终 Wiki 目录重名修复

## 故障与依据

诊断文件显示初读有 55 次缓存命中；目录规划在 213 个素材条目收敛至 14 章、61 个子主题后，以 `wiki_directory_duplicate_title` 中断。重试继续命中相同阶段。初读段数与目录素材条目数属于不同处理层级，不能据此推断材料丢失。

代码缺口在最终发布边界：独立目录窗口的名称只在各自窗口内校验，合并后仍可能重名；最终校验发生在原有请求纠错流程之外。旧的收敛断点恢复又把重名候选当作无效候选跳过，因此重试可能再次归并并重复失败。CSV 不含实际目录正文，无法从中确定具体哪些名称重复；复现使用人工构造的完整目录，不使用私人对话。

## 实施

- 候选目录可暂存重名，但所有材料归属、层级、数量与字段限制继续校验；最终发布必须通过严格唯一性校验。
- 最终目录只要存在重名，就对冲突标题发起一次有界命名请求。请求提供范围、分组与子主题，保留其他同级名称；只允许修改指定标题，不能重分材料、合并章节或删减来源。没有重名时不新增请求。
- 命名响应逐项检查缺失／重复／未知 ID、空值、长度、归一化重名及保留名称冲突；无效响应不进入成功缓存。成功结果单独保存为命名断点。
- 已完整核对材料归属的旧收敛候选即使重名，也能恢复到命名步骤。失败重试保留成功目录窗口和候选，不清空初读缓存；每次显式重试至多启动一次该命名步骤。
- 新请求使用主模型与独立预算，增加 `wiki:directory:names` 跟踪及 `nameRepairCount` 本地阶段计数。发布改为等待命名步骤，失败和取消仍进入正常的诊断／保留流程。
- 重名提示明确说明材料归属和分析已保留，未将不完整目录发布为成功结果。

## 验证

回归覆盖跨窗口合并重名、普通目录零新增请求、归一化冲突、无效响应不缓存、取消、保留其他标题及全部归属、旧候选恢复、成功命名断点复用、真实 AtlasAI facade 预算，以及“213 条目／14 章／61 子主题”在首次命名失败后仅重试命名的模拟场景。

`npm run check` 全部通过：521 个测试文件、3174 项测试通过；lint、类型检查、生产构建、Worker 验证及公开源码检查通过（1333 个公开文件）。保留既有快速刷新与构建体积提示，无新增 lint 错误。

实现直接位于桌面项目；完整检查包含本目录的生产构建。没有发送真实付费模型请求，没有修改用户浏览器内的项目或上传私人 CSV。真实材料需在加载新构建后重试验证。
