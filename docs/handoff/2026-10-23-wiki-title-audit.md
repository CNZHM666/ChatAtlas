# Wiki 标题生成盘查

日期：2026-10-23。本轮实现总览编辑按钮的位置调整；标题部分按用户要求盘查，未变更命名策略或自动改写已保存项目。

> 后续实施更新：用户已批准并实现完整优化。下文保留最初盘查时的复现结果；最新代码已修复专用预算、缓存接纳顺序、直写／重写路径覆盖，并把新项目命名纳入完整目录上下文。原有问题测试已转成防回归测试，详见 [实施记录](2026-10-23-wiki-quality-implementation.md)。这不表示已用真实模型验证所有材料的生成质量。

## 结论

确实存在请求预算、缓存接纳时机和路径覆盖上的缺口。当前标题修正是一个可失败的末尾命名步骤，不是覆盖所有产出路径的目录质量保证。继续只追加“不要 XX 与 XX”的提示词不足以解决这些问题。

截图中的大标题属于项目／文档总标题，不是 Wiki 章节标题。`DocumentOverview.tsx` 显示传入 title 或 session.title；`FocusWorkspace.tsx` 优先传入已保存项目名或空间名。现有 `wikiTitleEdits()` 只处理部分、章节、子主题，不处理这些项目名。没有这次运行的分析记录、实际扩展构建版本和保存数据，无法确认截图具体命中了哪条失败路径。

## 已用测试复现的问题

### 1. 标题请求预算在封装层被压低

`wiki-title-pass.ts` 申请 `min(2400, 300 + 标题数 * 60)`。但 `request-policy.ts` 没有给 `wiki_title_edit` 专用预算，回到通用 other：`300 + count * 220`；count 不读取 titles，因此通常为 1。`atlas-ai.ts` 再取请求额度和策略额度的较小值。

新增集成测试通过真实 AtlasAI facade 确认：10 个标题申请 900，fixture 模型实际收到 520。部分模型的 reasoningReserve 会使实际数字有所不同，但遗漏标题专用策略的事实不变。规模较大时可能截断或漏项；是否导致用户这次运行失败仍需运行记录确认。

原 `wiki-title-pass.test.ts` 直接模拟 generateStructured，未经过这个预算封装，因此测试能通过而真实额度仍然偏小。

### 2. 不可用的改名会被缓存，重跑也不自愈

标题请求的 validate 只验证 titles 是数组并提取字符串。空数组、遗漏 ID、仍然并列的标题都能通过这层验证。AtlasAI 缓存这个结果后，`wikiTitleEdits()` 才做并列、长度、重复检查并拒绝改名。

新增测试：第一次模型返回仍为“产品定位与竞品”的建议，本地拒绝；第二个运行发送同一请求，仍然无改名，provider 总调用只有一次，证明重复命中了已缓存的无效建议。成功且有效的改名缓存应保留；需要区分可用项、拒绝项和未返回项，避免无效结果成为反复复用的成功缓存。

### 3. 短对话直写不经过标题修正

`focus-coverage.ts` 只有 final + topicPlan + work + generateStructured 才启动标题修正。短对话 direct 路径没有 topicPlan。后续 `autoOrganizeWiki()` 对少于两个可整理章节直接标记 protected；这个状态表示没有可合并目录，不代表标题已经通过编辑。

新增测试确认：短来源产生一个“产品定位与竞品”章节，标题请求从未发生，经过 autoOrganizeWiki 和 requireOrganizedWiki 后仍可发布原标题。多章节直写会进入后置目录整理，但该整理也没有调用独立的 wikiTitleEdits。

### 4. 文档总标题沿用第一份写作结果

`joinedResults()` 对多个写作批次保留第一份响应的 title，并不基于整个目录另选一个项目名。新增测试确认：即使章节导航已改为“产品定位”，文档总标题仍可以是第一批响应的“产品定位与竞品”。若第一批主要讨论定位和竞品，这个局部标题可能被带到整份项目文档；这是代码可发生的行为，不能据截图证明它一定是本次标题的来源。已保存的空间名还会优先于 session.title 显示。

## 其他设计限制

- `focus-coverage.ts` 对标题请求 `.catch(() => undefined)`，保留原目录继续发布。保证正文可用是合理的，但用户侧看不出标题编辑是成功、部分成功、失败还是被跳过；已有通用用量事件不能解释逐项拒绝原因。
- 最终 assertWikiOutline 校验章节数量、重名、长度、层级；不校验“单一主体”。当前代码明确避免按标点一刀切，这个原则应保留。“导入与导出”等合法复合主题不应因为有“与”就被拆开。
- 独立标题编辑只读标题和截取到 400 字的导航上下文，不读取完整正文；并且不能移动材料归属。它最多修复表达，不能修复一个章节同时拥有两个独立主题的结构。提示模型选择“dominant subject”还可能让简短标题不能完整表达章节范围，正文和证据虽未删除，目录标签却可能失真。
- `renameWikiHeadings()` 仅替换与计划名完全一致的 `##` 小标题；这是有意的保守策略。不同 Markdown 包装是否被上游正规化需逐例分析，不能把所有正文标题都当作已经修正。
- 增量更新、单章重写也有自己的标题路径，不共享这个标题步骤。已保存内容在普通阅读时不会重新调用模型；个人改名必须受到保护，不能用修正并列标题的名义覆盖。

## 建议修复顺序

1. 先修标题请求的真实输出预算，按待处理项有界分批；将语义接纳与可缓存性关联，并保留有效的部分成果。不要清空材料阅读缓存或重写正文。
2. 为命名编辑建立统一的最终接入点，覆盖目录写作、直写后整理及新增／重写章节；记录跳过、失败和逐项拒绝原因。保留正文生成成功这一成果。
3. 分开定义项目总标题与章节标题：项目名基于整个范围，已保存和个人修改的名字保留。不能直接把第一章的标题当作整个项目名。
4. 在目录阶段判断主体归属，发现真实混合主题时调整材料归属，不能靠删除连接词假装结构已改善。标题编辑阶段只负责命名，不承担重新规划目录的职责。
